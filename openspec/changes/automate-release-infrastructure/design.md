## Context

rvw 0.2.0 was released from a tag whose runtime version and package metadata had diverged. The existing tag-triggered workflow correctly gates, builds, and publishes with PyPI OIDC, but version preparation is manual and its GitHub release job assumes that no release already exists. GitHub also suppresses follow-on workflow events created with the repository `GITHUB_TOKEN`, so a release-please-created tag cannot reliably trigger a separate tag workflow without a PAT.

The repository already uses tag-pinned GitHub Actions and has a deterministic offline gate suite. The new design must work with only `github.token`, retain the tag-push emergency path, and leave the external rvw registry untouched.

## Goals / Non-Goals

**Goals:**

- Make release-please the sole writer of all checked-in version surfaces and `CHANGELOG.md`.
- Run the existing gates, build, PyPI OIDC publication, and release-asset publication for both automated releases and manually pushed version tags.
- Provide conservative dependency, stale-item, contribution, security, ownership, template, and labeling automation appropriate to a single-maintainer Python project.
- Preserve the current CI matrix and release verification gates.

**Non-Goals:**

- Add beta channels, Docker, Bun, Windows-startup, all-contributors, or Codex-review automation.
- Modify the rvw runtime registry or CLI review behavior.
- Require a PAT, PyPI token, or other new secret.

## Decisions

### Release preparation has one automated writer

release-please uses the Python release type so its release PR updates `pyproject.toml` and `CHANGELOG.md`. Extra-file updaters synchronize the annotated assignment in `src/rvw/_version.py` and the root `rvw` package entry in `uv.lock`. The manifest starts at `0.2.0`, preventing the already-published version from being proposed again.

Manual changes to `CHANGELOG.md` are prohibited by contribution policy. The existing version-sync regression test remains a local guard, while the release workflow validates the selected tag against both package metadata and runtime version before building.

### Automated publishing calls the release chain directly

`.github/workflows/release.yml` accepts `workflow_call` with a required tag and retains `push.tags: ["v*"]`. The release-please workflow exposes the action's `release_created` and `tag_name` outputs and conditionally calls that reusable workflow with explicit `contents: write` and `id-token: write` permissions.

This direct call avoids relying on a tag-push event generated by `GITHUB_TOKEN`, which GitHub does not recursively dispatch to another workflow. A configured `RELEASE_PLEASE_TOKEN` remains an optional way to obtain normal PAT-triggered event behavior; the expression falls back to `github.token` without changing the direct-call path.

### One tag input controls every release job

The reusable workflow resolves `inputs.tag` for calls and `github.ref_name` for tag pushes, checks out that explicit ref in gate/build/release jobs, and compares it with both checked-in version values. This keeps manual and automated entry points equivalent and prevents a branch checkout or stale package version from reaching PyPI.

release-please creates the GitHub release before the reusable workflow runs. Therefore the final job uploads artifacts to an existing release when present and creates a release only for the emergency tag-push path. This makes the final stage idempotent across both callers.

### Repository automation is deliberately narrow

Dependabot covers only uv and GitHub Actions. Stale handling uses long 60-day/14-day windows and exempts `pinned` and `security`. The PR labeler uses `pull_request_target` only to apply base-repository path rules and never checks out or executes PR code. Documentation makes `rvw gate --target <pr>`, green CI, mergeability, Conventional Commits, and OpenSpec changes explicit merge requirements.

## Risks / Trade-offs

- [A PAT-generated tag also triggers the tag workflow while the direct reusable call runs] → Both entry points use the same artifact version, release jobs share a tag concurrency key, PyPI skips an already-existing identical artifact, and release assets upload with `--clobber`; the direct call remains the authoritative no-secret path.
- [The PyPI environment is configured to trust only one workflow filename] → The actual OIDC job remains in `release.yml`; callers only invoke it, preserving the trusted workflow identity.
- [A release exists before PyPI publication completes] → release-please necessarily creates it first; failed publish runs remain visible and rerunnable, while release assets are attached only after successful PyPI publication.
- [Path labels or hygiene labels do not yet exist] → Workflows do not create labels automatically; maintainers must create the documented labels once.

## Migration Plan

Merge the release-please configuration and workflows on `main` with the manifest at `0.2.0`. Future Conventional Commits accumulate into a release PR; merging that PR creates the next tag and GitHub release and directly invokes publication. If automation is unavailable, a maintainer can still push a correctly synchronized `vX.Y.Z` tag to invoke the same chain.

Rollback consists of disabling the release-please workflow and using the retained tag path. No registry or published artifact migration is required.

## Open Questions

None. Label creation and an optional release-please PAT are repository-administration steps rather than implementation blockers.
